# PATH_LOGGING.md — เดินเก็บเส้นทาง (ทำทางเองในที่ที่ไม่มีทาง)

เดินไปตามทางที่อยากให้เป็นเส้นทาง แล้วแอปจะ **บันทึกเส้นที่เดินไว้เป็นเส้นทางจริง**
ที่นำทางตามได้ ดูย้อนหลังได้ และส่งออกเป็นไฟล์ไปใช้ต่อได้ — ทำงานออฟไลน์ 100%

> เข้าใช้งาน: **ตั้งค่า → สำหรับผู้ดูแล → เดินเก็บเส้นทาง (มีแผนที่)** หรือ **(โหมดตัวเลข)**
> โค้ด: `ui/pathlog/` · `survey/TrackRecorder.kt` · `data/geojson/TrackLogExporter.kt`

---

## 0. ระบบนี้มีไว้ทำอะไร

**สำหรับพื้นที่ที่ไม่มีเส้นทางอยู่ในข้อมูลใด ๆ เลย** — ในป่า ในพื้นที่ที่ OpenStreetMap
และ Google Maps ไม่มีทางเดินให้ ทางที่ต้องการมีอยู่จริงบนพื้นดิน แต่ไม่มีในไฟล์ไหน

วิธีแก้คือ **เดินมันเอง** แล้วเส้นที่เดินนั่นแหละกลายเป็นเส้นทาง จากนั้นค่อยเอา basemap
มาวางข้างใต้ทีหลัง (หรือไม่วางเลยก็ได้) เพราะพิกัดที่ได้เป็น **WGS84 สัมบูรณ์**
ไม่ได้อ้างอิงกับแผนที่ใบไหน จึงตรงเสมอไม่ว่าจะเอาอะไรมารองข้างใต้

> **ห้ามจิ้มพิกัดจาก Google Maps มาใส่แทน** ภาพดาวเทียม Google มี offset กับข้อมูลจริง
> 3–15 ม. ส่วนเส้นที่เดินเก็บเองมาจากเครื่องรับตัวเดียวกับที่จะใช้นำทาง offset จึงหักล้างกัน
> (เหตุผลเดียวกับ `ACCURACY.md` A1)

## 1. สองโหมด ชุดข้อมูลเดียว

| | **โหมดแผนที่** (`PathLogScreen`) | **โหมดตัวเลข** (`PathReadoutScreen`) |
|---|---|---|
| เห็นอะไร | แผนที่ + หมุดตัวเอง + เส้นที่กำลังเดิน + **เส้นที่เก็บไว้แล้วทุกเส้น** | ตัวเลขจากเครื่องรับล้วน ๆ ครบทุกค่า |
| เหมาะกับ | ตอนต้องรู้ว่า "เดินครบหรือยัง" เส้นไหนยังขาด | เดินยาว ๆ ในที่ที่รู้ทางอยู่แล้ว |
| ข้อดี | เห็นช่องว่างระหว่างเส้นทันที ซึ่งเป็นคำถามหลักของการทำแผนที่ | เปิดเร็ว กินแบตน้อย (ไม่ต้อง render แผนที่) |
| ค่าเพิ่มที่เห็น | — | ความเร็ว · ทิศทาง · **อายุ fix ล่าสุด** · fix ที่ถูกทิ้ง |
| บันทึกเป็น | `captureMode: "map"` | `captureMode: "readout"` |

**อายุ fix สำคัญมากตอนเดินเก็บเส้นทาง** ถ้าเครื่องหยุดรายงานแต่ค่าความคลาดเคลื่อนยังดูดี
เส้นจะถูกลากตรงข้ามสิ่งที่เดินจริงไปเงียบ ๆ โหมดตัวเลขจึงโชว์ค่านี้ไว้ตลอด

## 2. เดินเก็บยังไง

1. เปิดหน้าใดหน้าหนึ่ง รอให้จับสัญญาณได้ (ปุ่มจะกดไม่ได้จนกว่าจะมี fix)
2. กด **"เริ่มเดินเก็บเส้นทาง"** แล้ว **เดินไปตามทางจริง ๆ** ด้วยความเร็วปกติ
3. ถึงปลายทางกด **"หยุดแล้วใช้เส้นนี้"**
4. ตั้งชื่อว่าอะไร เช่น `ทางไปน้ำตก` แล้วเลือกว่าจะ **ใช้เส้นนี้นำทาง** ไหม (เปิดไว้เป็นค่าเริ่มต้น)
5. กด **บันทึกเส้นทางนี้** → เส้นเข้าระบบนำทางทันที ไม่ต้อง export ไม่ต้อง rebuild

### ตัวกรอง 2 ชั้นที่ทำให้เส้นใช้ได้จริง

| ชั้น | ทำอะไร | ทำไม |
|---|---|---|
| **ระยะห่างขั้นต่ำ 3 ม.** | fix ที่ใกล้จุดก่อนหน้ากว่านี้ไม่กลายเป็นจุดของเส้น | ยืนนิ่ง 1 นาทีไม่ควรได้ 60 จุดซ้อนกัน |
| **Douglas-Peucker 2 ม.** (ตอนกด หยุด) | ตัดจุดที่ไม่ใช่หัวเลี้ยวทิ้ง | เหลือแต่จุดที่เป็นมุมจริง ไฟล์เล็กลง กราฟเร็วขึ้น |

**ระยะทางที่บันทึกวัดจากเส้นก่อนถูกลดจุด** เพราะคนถามว่า "เดินไปกี่เมตร" ไม่ได้ถามว่า
"เส้นที่ทำความสะอาดแล้วยาวเท่าไร"

### เกณฑ์ความคลาดเคลื่อนหลวมกว่าการเก็บจุด (ตั้งใจ)

`TrackRecorder.DEFAULT_MAX_ACCURACY_M = 20 ม.` เทียบกับการเก็บจุดที่ 15 ม.

ยืนนิ่ง 30 วินาทีรอ fix ดี ๆ ได้ แต่**เดินอยู่รอไม่ได้** ใต้ทรงพุ่มหนา 10–20 ม. คือค่าปกติ
ถ้าตัดทิ้งหมดจะไม่ได้เส้นเลย ในที่ที่ไม่มีแผนที่อยู่แล้ว ซึ่งแย่กว่าได้เส้นที่หยาบหน่อย
fix พวกนี้ผ่านด่าน 25 ม. ของแอปมาแล้ว (`ACCURACY.md` A4) และความหยาบถูก**บันทึกไว้** ไม่ได้ซ่อน

## 3. เก็บแล้วทำอะไรได้ต่อ

### ดูย้อนหลัง

- **โหมดแผนที่:** เส้นทุกเส้นวาดอยู่บนแผนที่ สีตามคุณภาพของการเดิน (เขียว ≤5 ม. ·
  ส้ม ≤10 ม. · แดง >10 ม. — เกณฑ์เดียวกับหมุด GPS) มีป้ายรหัส `T001` กำกับ
  **แตะที่เส้นเพื่อเปิดรายละเอียด**
- **ทั้งสองโหมด:** รายการเส้นทาง เรียงตามลำดับที่เดิน แสดงชื่อ + รหัส + ระยะ + ความคลาดเคลื่อน

### เลือกว่าเส้นไหนจะใช้นำทาง

สวิตช์ **"ใช้เส้นนี้นำทาง"** ในหน้ารายละเอียดของแต่ละเส้น

| สถานะ | ผล |
|---|---|
| เปิด | เส้นเข้ากราฟ routing · วาดทึบบนแผนที่ |
| ปิด | ยังเก็บเป็นข้อมูลและยังส่งออกได้ · **วาดจาง** · ไม่มีใครถูกพาเดินไปตามนี้ |

**ทำไมต้องมีสวิตช์:** การสำรวจย่อมมีเส้นที่เดินผิด — ทางที่กลายเป็นทางเข้าบ้านคน
เส้นที่เดินซ้ำสองรอบ **ปิดไม่ใช่ลบ** เพราะ "เคยเดินตรงนี้แล้ว" มีค่าตอนกลับมาสำรวจรอบหน้า
**ลบ** ไว้ใช้เฉพาะตอนที่ไม่ควรบันทึกตั้งแต่แรก

> อยากใช้เฉพาะเส้นที่เดินเอง ไม่เอาข้อมูล OSM เลย →
> **ตั้งค่า → "ใช้เฉพาะเส้นทางที่สำรวจเอง"** เหมาะกับงานในป่าที่ข้อมูล OSM ไม่มีอะไรเลย

## 4. ค่าที่เก็บและส่งออก

**มีแต่ค่าที่วัดได้ กับชื่อที่คนตั้งเอง 1 ช่อง** ไม่มีชื่ออาคาร ไม่มีคณะ ไม่มีหมวดหมู่
ไม่มีประเภททาง ไม่มี "มีไฟไหม" "มีหลังคาไหม" — ของพวกนั้นเป็นเรื่องของ POI ไม่ใช่ของการวัด
(กฎเดียวกับ `GPS_LOGGING.md` §1)

| ฟิลด์ | หน่วย / รูปแบบ | ความหมาย | ทำไมต้องมี |
|---|---|---|---|
| `code` | `T001` | รหัสวิ่งตามลำดับที่เดิน | เลขไม่ถูกใช้ซ้ำแม้ลบเส้นทิ้ง |
| *(geometry)* | `LineString` องศา WGS84 ทศนิยม 7 ตำแหน่ง | ตัวเส้นทาง | **นี่คือของจริงที่ทั้งระบบมีไว้ผลิต** |
| `lengthMeters` | เมตร | ระยะที่เดินจริง (วัดก่อนลดจุด) | คู่กับ `vertexCount` บอกว่าเส้นละเอียดแค่ไหน |
| `vertexCount` | จุด | จำนวนจุดหักหลังลดจุดแล้ว | เส้น 500 ม. ที่เหลือ 3 จุด = เดินตรงมาก หรือสัญญาณขาด |
| `averageAccuracyMeters` | เมตร | ความคลาดเคลื่อนเฉลี่ยตลอดการเดิน | ตัวตัดสินว่าเส้นนี้เชื่อได้แค่ไหน |
| `worstAccuracyMeters` | เมตร | fix ที่แย่ที่สุดที่ยังรับไว้ | **ค่าเฉลี่ยดีปิดบังหัวโค้งเดียวที่เดินใต้ต้นไม้ได้** |
| `satellitesUsed` / `satellitesVisible` | ดวง | ค่ามัธยฐานตลอดการเดิน | เห็นเยอะแต่ใช้ได้น้อย = โดนทรงพุ่มบัง |
| `fixCount` | ครั้ง | fix ที่รับไว้ (ก่อนกรองระยะห่าง) | เทียบกับ `durationSeconds` แล้วรู้ว่าสัญญาณขาดช่วงไหม |
| `rejectedCount` | ครั้ง | fix ที่ทิ้งเพราะคลาดเคลื่อนเกิน 20 ม. | สูง = เส้นนี้ควรกลับไปเดินซ้ำ |
| `durationSeconds` | วินาที | เวลาที่ใช้เดิน | เดิน 300 ม. ใน 30 วินาที = ไม่ได้เดิน |
| `recordedAt` | ISO-8601 มี offset | เวลาที่เดิน | ย้อนดูสภาพใบไม้/เวลาของวันได้ |
| `captureMode` | `map` / `readout` | เก็บจากหน้าจอไหน | ดู §1 |
| `usedForRouting` | `true` / `false` | เปิดใช้นำทางอยู่ไหม | คนที่รับไฟล์ไปควรรู้ว่าเส้นไหนเจ้าของตั้งใจให้ใช้ |
| `note` | ข้อความไทยได้ | ชื่อที่คนตั้ง | ฟิลด์**เดียว**ที่แก้ทีหลังได้ นอกนั้นคือค่าที่วัดมา |

### ค่าที่ตั้งใจ *ไม่* เก็บ

| ไม่เก็บ | เหตุผล |
|---|---|
| ชื่ออาคาร / คณะ / หมวดหมู่ | นั่นคือ POI ไม่ใช่การวัด — ใช้โหมดสำรวจพิกัดแทน |
| ประเภททาง (ทางเท้า/ถนน/บันได) | เป็นการบรรยายทาง ไม่ใช่สิ่งที่เครื่องวัดได้ · ตอนเข้ากราฟ routing ถือเป็น `footway` ทั้งหมด |
| มีไฟ / มีหลังคา / เดินทางเดียว | 3 คำถามที่ตอบด้วยการเดา ขณะยืนตากแดดอยู่ปลายทาง |
| พิกัดดิบทุก fix | `fixCount` + `rejectedCount` + `worstAccuracy` สรุปคุณภาพครบแล้ว โดยไฟล์ไม่บวม |

## 5. ไฟล์ที่ส่งออก

กด **ส่งออก** มุมขวาบน เลือกได้ว่าจะเอาทั้งหมด / เฉพาะโหมดแผนที่ / เฉพาะโหมดตัวเลข
ชื่อไฟล์: `tracks_20260920_1432.geojson` หรือ `.csv`

### 5.1 GeoJSON — ตัวหลัก

`FeatureCollection` ของ `LineString` ตาม RFC 7946 เปิดใน **QGIS / umap / josm** ได้ทันที

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "LineString",
        "coordinates": [[101.3529617, 14.1610243], [101.3531617, 14.1612243]]
      },
      "properties": {
        "code": "T001",
        "lengthMeters": 31.2,
        "vertexCount": 2,
        "averageAccuracyMeters": 7.5,
        "worstAccuracyMeters": 13.2,
        "satellitesUsed": 9,
        "satellitesVisible": 17,
        "fixCount": 42,
        "rejectedCount": 3,
        "durationSeconds": 48,
        "recordedAt": "2026-09-20T14:32:05+07:00",
        "captureMode": "map",
        "usedForRouting": true,
        "note": "ทางไปน้ำตก"
      }
    }
  ]
}
```

### 5.2 CSV — หนึ่งแถวต่อหนึ่งเส้นทาง

คอลัมน์สุดท้าย `wkt` เก็บรูปเส้นเป็น `LINESTRING(lon lat, lon lat, ...)`
QGIS อ่านได้ตรง ๆ ผ่าน **Add Layer → Add Delimited Text Layer → Geometry: Well known text**

เลือกหนึ่งแถวต่อเส้น (ไม่ใช่หนึ่งแถวต่อจุด) เพราะคนส่วนใหญ่เปิดไฟล์นี้ใน Excel
ถ้าแตกเป็นจุดละแถว ค่าที่วัดได้จะซ้ำเป็นร้อยรอบจนอ่านไม่รู้เรื่อง

> ข้อจำกัด: ช่องเดียวใน Excel เก็บได้ ~32,000 ตัวอักษร ≈ 1,400 จุด ถ้าเส้นยาวกว่านั้น
> ให้ใช้ GeoJSON ตัวเลขทั้งหมดใน CSV ยังถูกต้องเสมอ

CSV มี **BOM UTF-8 + CRLF** ไม่งั้น Excel บน Windows อ่านชื่อเส้นภาษาไทยเป็นตัวยึกยือ

### 5.3 เอาไปทำแผนที่ต่อ

1. เปิด `tracks_*.geojson` ใน **QGIS**
2. อยากมีภาพพื้นหลัง → เพิ่ม XYZ layer ของภาพดาวเทียม
   **ถ้าภาพกับเส้นไม่ตรง ให้เชื่อเส้น ไม่ใช่ภาพ** (เหตุผลใน §0)
3. อยากให้แอปเองมี basemap ในพื้นที่นั้น → แก้ `assets/config/campus_config.json`
   (`bbox` / `center`) แล้วสร้าง MBTiles เอง โหมด `BUNDLED` — ดู `OFFLINE.md`

## 6. เส้นทาง ≠ จุดพิกัด GPS ≠ POI ≠ จุดอันตราย

ตอนนี้แอปมี 4 ระบบที่เก็บพิกัด และตั้งใจแยกกันหมด **อย่ารวม**

| | POI (`ui/survey/`) | จุด GPS (`ui/gpslog/`) | **เส้นทาง (`ui/pathlog/`)** | จุดอันตราย (`ui/hazard/`) |
|---|---|---|---|---|
| รูปทรง | จุด | จุด | **เส้น** | จุด + รัศมี |
| ตอบคำถามว่า | "ที่นี่คืออะไร" | "เครื่องวัดได้เท่าไร" | **"เดินจากตรงนี้ไปตรงนั้นยังไง"** | "ตรงนี้อันตราย" |
| เข้ากราฟ routing | เข้า (เป็นจุดหมาย) | ไม่เข้า | **เข้า ถ้าเปิดสวิตช์** | ไม่เข้า |
| ตารางใน Room | `poi` | `gps_point` | `track_log` | `hazard_point` |
| ไฟล์ export | `pois_surveyed.geojson` | `gps_points_*` | `tracks_*.geojson/.csv` | `hazards.geojson` |

**เส้นทางเป็นระบบเดียวที่เข้ากราฟ routing ได้** เพราะมันคือสิ่งที่นำทางไปตามได้จริง
ส่วนอีกสามระบบเป็นจุด ซึ่งบอกไม่ได้ว่าจะเดินจากจุดหนึ่งไปอีกจุดยังไง

> **ควรใช้อันไหนสำหรับงานทำแผนที่ในป่า** — ใช้ **เดินเก็บเส้นทาง** เป็นหลัก
> ส่วน **เก็บพิกัด GPS** ใช้เสริมเฉพาะจุดสำคัญ (ปากทาง แยก จุดสังเกต) เพราะจุดหนึ่งจุด
> เฉลี่ยจาก 30 fix ด้วย median จึงแม่นกว่าจุดใด ๆ บนเส้นทางมาก ใช้เป็นหมุดยึดตรวจสอบเส้นได้

## 8. ถ้าจะแก้ต่อ อ่านตรงนี้ก่อน

- **อย่าเพิ่มฟิลด์ที่ไม่ใช่ค่าที่วัดได้** ลงใน `TrackLog` ถ้าอยากได้ชื่ออาคาร/หมวดหมู่
  นั่นคือ POI — ระบบนี้เคยอยู่รวมกับหน้าสำรวจ POI แล้วมันถามหาคณะกับอาคาร
  ในพื้นที่ที่ไม่มีอาคารเลย นั่นคือเหตุผลที่แยกออกมา
- เพิ่มฟิลด์ใหม่: `TrackLog` → `TrackLogEntity` (+ migration ใหม่ DB version +1)
  → `TrackLogExporter` ทั้ง GeoJSON และ CSV (`CSV_HEADER` ด้วย) → ตารางใน §4
  → test ใน `TrackLogExporterTest`
- **เส้นที่ปิดสวิตช์ต้องไม่หายไปจากจอ** ให้วาดจาง เพราะมันคือบันทึกว่าเคยเดินตรงนั้น
- `ui/gpslog/` (จุด) กับ `ui/pathlog/` (เส้น) **คนละระบบ ห้ามรวม** แต่ให้หน้าตาสอดคล้องกัน
  ทั้งคู่ใช้เกณฑ์สี 5/10 ม. เดียวกัน และ dialog ส่งออกหน้าตาเดียวกัน
- ถ้าจะทำให้ routing แยกประเภททางได้อีกครั้ง **อย่าเอากลับมาถามตอนกดหยุดเดิน**
  ให้ไปแก้ทีหลังในหน้ารายละเอียดแทน ตอนกดหยุดคนยังยืนอยู่กลางแดดปลายทาง
