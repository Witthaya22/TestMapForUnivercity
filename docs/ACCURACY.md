# ACCURACY.md — ทำไมหมุดไม่ตรง และแก้ยังไง

เอกสารนี้เขียนเพราะปัญหา *"จุดของเราไม่ตรงกับแผนที่"* เป็นปัญหาที่เจอบ่อยที่สุด
และเกือบทุกครั้ง **ไม่ได้เกิดจาก GPS เสีย** แต่เกิดจากข้อมูลแผนที่หรือวิธีเขียนโค้ด

---

## สรุปสาเหตุทั้ง 8 ข้อ และวิธีที่แอปนี้แก้

### A1 — ก็อปพิกัดจาก Google Maps มาแปะบน basemap ที่ทำจาก OSM
**นี่คือสาเหตุอันดับ 1**

ภาพดาวเทียมที่ Google ใช้ กับข้อมูลเวกเตอร์ของ OpenStreetMap ไม่ได้ผูกกับกริดเดียวกัน
ภาพดาวเทียมทุกเจ้ามี *orthorectification offset* ซึ่งในไทยเจอได้ **3–15 เมตร**
พอคุณเปิด Google Maps → คลิกขวา → copy พิกัด → เอามาวางในแอปที่ render จาก OSM
หมุดจะไปโผล่กลางสนามแทนที่จะอยู่ตรงประตู ทั้งที่ตัวเลขพิกัด "ถูก" ในระบบของ Google

ยิ่งกว่านั้น OSM ในเขตมหาวิทยาลัยไทยมักวาดไม่ครบ — ในมอนี้มีถนน 95 เส้นแต่ทางเดินแค่ 51 เส้น
แอปจึง **นำทางบนถนนในมอด้วย ไม่ใช่แค่ทางเท้า** และมีโหมดบันทึกเส้นทางไว้เติมส่วนที่ขาด

**วิธีแก้ในแอปนี้:** ห้ามก็อปจาก Google เด็ดขาด แหล่งพิกัดที่ใช้ได้มี 2 ทาง:

| แหล่ง | offset เทียบ basemap | ใช้เมื่อไร |
|---|---|---|
| **Surveyor Mode** ในแอป | ศูนย์โดยนิยาม — GPS เครื่องเดียวกับที่ใช้นำทางเป็นคนบอกพิกัด | จุดที่ต้องการความแม่นระดับเมตร |
| **OpenStreetMap** ผ่าน `tools/osm_import.py` | ศูนย์เชิงระบบ — เป็นชุดข้อมูลเดียวกับที่ basemap วาดมา | ข้อมูลตั้งต้น ให้แอปใช้ได้ทันทีก่อนออกสำรวจ |

ที่ OSM ไม่มีปัญหาแบบ Google เพราะ tile ที่แอป render **ทำมาจากข้อมูล OSM ชุดเดียวกัน**
พิกัดกับภาพจึงอยู่บนกริดเดียวกันเสมอ ไม่ว่าข้อมูลนั้นจะตรงกับโลกจริงแค่ไหนก็ตาม

แต่ระวัง: *ตรงกับ basemap* ไม่ได้แปลว่า *ตรงกับโลกจริง* รูปอาคารใน OSM ลากจากภาพถ่าย
และรั้วมอติด tag `note=Outline completly estimated.` ไว้ตรง ๆ จุดจาก OSM จึงติดธง
`needsSurvey: true` ไว้ทุกจุด และควรถูกเดินเก็บทับด้วย Surveyor Mode

### A2 — ใช้ provider ที่ไม่แม่น
`NETWORK_PROVIDER` หาตำแหน่งจาก cell tower / Wi-Fi → คลาดเคลื่อน **100–2000 เมตร**
`FusedLocationProvider` แบบ `PRIORITY_BALANCED_POWER_ACCURACY` ก็ใช้ตัวนี้เป็นหลัก

**วิธีแก้:** `GpsLocationSource.kt` เรียก `LocationManager` ด้วย `GPS_PROVIDER` เท่านั้น
และ manifest ประกาศ `<uses-feature android:name="android.hardware.location.gps" android:required="true" />`
(ข้อดีพ่วง: ไม่พึ่ง Google Play Services เลย ทำให้ทำงานบนเครื่องที่ไม่มี GMS ได้)

---

### A3 — ไม่รอ GPS lock
GPS cold start ตอน **ไม่มีเน็ต** ต้องดาวน์โหลด almanac/ephemeris จากตัวดาวเทียมเอง
ใช้เวลา **30–90 วินาที** (ถ้ามีเน็ตจะได้ A-GPS มาช่วยเหลือเหลือ 5–10 วิ)

ถ้าแสดงหมุดทันทีที่ได้ fix แรก ผู้ใช้จะเห็นหมุดกระโดดข้ามมอไปมาแล้วสรุปว่า "แอปพัง"

**วิธีแก้:** ระหว่างรอ แสดง overlay
> กำลังหาสัญญาณดาวเทียม… (ความแม่นยำ XX ม.)

และ **ไม่แสดงหมุดตัวเองเลย** จนกว่าจะได้ fix ที่ `accuracy < 20 m`

### A4 — ไม่กรอง fix ห่วย
ทิ้ง location fix ที่:

| เงื่อนไข | เหตุผล |
|---|---|
| `accuracy > 25 m` | แม่นไม่พอสำหรับนำทางในมอที่ทางเดินห่างกัน 10–20 ม. |
| `elapsedRealtimeNanos` เก่ากว่า 10 วินาที | เป็น cached fix จากแอปอื่น อาจเป็นตำแหน่งเมื่อวาน |
| ความเร็วที่คำนวณได้ > 10 m/s | คนเดินไม่ได้เร็วขนาดนั้น = fix กระโดด |

### A5 — สลับ lat / lon
**GeoJSON ใช้ `[longitude, latitude]`** ตาม RFC 7946
**MapLibre ใช้ `LatLng(latitude, longitude)`** — สลับกัน

ที่ปราจีนบุรี lat ≈ 14 และ lon ≈ 101 ถ้าสลับกันจะได้จุดที่ (101 N, 14 E) ซึ่งอยู่ขั้วโลกเหนือ
— เห็นชัดทันที แต่ถ้าอยู่แถวเส้นศูนย์สูตรอาจไม่ทันสังเกต

**วิธีแก้:** แปลงที่ `core/geo/GeoUtils.kt` **ที่เดียว** ผ่าน helper ที่ตั้งชื่อชัดเจน
ห้ามเขียน `LatLng(coords[0], coords[1])` กระจายตามไฟล์
มี unit test ที่ assert ว่าทุก POI อยู่ใน bbox — ถ้าสลับจะ fail ทันที

### A6 — เอาพิกัด UTM มาปนกับ WGS84
ไฟล์รังวัดจากกรมที่ดิน/ช่างสำรวจในไทยมักเป็น **UTM Zone 47N (EPSG:32647)**
ซึ่งมีหน้าตาแบบ `E 731234.5, N 1560987.2` — ไม่ใช่องศา

**วิธีแก้:** validator ตรวจว่าค่าอยู่ในช่วง `lon ∈ [-180, 180]`, `lat ∈ [-90, 90]`
ถ้าเกิน จะ throw พร้อมข้อความไทยบอกให้แปลง CRS ก่อน

---

### A7 — Marker anchor ผิด
ถ้าไอคอนหมุดเป็นรูปหมุดปักที่มีปลายแหลมด้านล่าง แต่ตั้ง anchor เป็น `center`
ปลายหมุดจะอยู่ **ต่ำกว่า** พิกัดจริงครึ่งความสูงไอคอน = เพี้ยน 10–20 px
ที่ z17 คือประมาณ **5–10 เมตร**

**วิธีแก้:** ไอคอนหมุดตั้ง `ICON_ANCHOR_BOTTOM`
จุดตำแหน่งผู้ใช้ (วงกลม) ตั้ง `ICON_ANCHOR_CENTER` เพราะเป็นวงกลมสมมาตร

---

### A8 — ตำแหน่งกระตุก
GPS มี noise ประมาณ ±3–5 ม. ตลอดเวลาแม้ยืนนิ่ง หมุดจะสั่นไปมา ดูเหมือนแอปพัง

**วิธีแก้:** `GpsKalmanFilter.kt` — Kalman filter 1 มิติ ที่ใช้ `accuracy` ของแต่ละ fix
เป็น measurement variance และมี process noise `Q ≈ 1.0 m/s`
fix ที่แม่นกว่าจะถูกเชื่อมากกว่าโดยอัตโนมัติ

## หน้า Debug GPS

เปิดจาก **ตั้งค่า → แตะโลโก้ 7 ครั้ง**

แสดงสด ๆ:
- provider ที่กำลังใช้
- lat / lon ทศนิยม 7 ตำแหน่ง (7 ตำแหน่ง ≈ 1 ซม. ละเอียดเกินพอ)
- accuracy (ม.)
- จำนวนดาวเทียมที่เห็น / ที่ใช้จริงในการคำนวณ (`GnssStatus.Callback`)
- speed, bearing
- เวลาตั้งแต่ fix ล่าสุด
- **ระยะห่างจากเส้นทางเดินที่ใกล้ที่สุด**

บรรทัดสุดท้ายสำคัญมากตอนออกภาคสนาม เพราะมันแยกได้ว่า:

| อาการ | แปลว่า |
|---|---|
| accuracy ดี (< 8 ม.) แต่ห่างเส้นทาง 30 ม. | **ข้อมูลแผนที่ผิด** → ไปสำรวจเส้นทางใหม่ |
| accuracy แย่ (> 20 ม.) และห่างเส้นทางมาก | **GPS ยังไม่นิ่ง** → รอ หรือเดินออกจากตึก |
| ดาวเทียมที่ใช้ < 4 ดวง | คำนวณตำแหน่ง 3 มิติไม่ได้ → ค่าที่ได้เชื่อไม่ได้เลย |

## ข้อจำกัดที่แก้ไม่ได้

- **ในอาคาร GPS ใช้ไม่ได้** สัญญาณดาวเทียมทะลุหลังคาคอนกรีตไม่ได้
  แอปจะค้างที่ fix สุดท้ายก่อนเข้าอาคารและขึ้นเตือนว่าสัญญาณอ่อน
- **ใต้ต้นไม้ทึบหรือระหว่างตึกสูง** เจอ multipath — สัญญาณสะท้อนกำแพงทำให้คลาดเคลื่อน 10–30 ม.
- **cold start ไม่มีเน็ต ช้า 30–90 วินาที** เป็นข้อแลกเปลี่ยนของการไม่พึ่ง A-GPS
  ถ้าเปิดแอปครั้งแรกในมอตอนไม่มีเน็ต ให้ยืนกลางแจ้งรอสักครู่
- **นำทางในอาคารไม่ได้** ด้วยเหตุผลเดียวกัน `tools/osm_import.py` จึงตัดทางเดินที่ติด tag
  `indoor` / `level` / `highway=corridor` ทิ้งทั้งหมด — เส้นทางที่นำทางตามไม่ได้จริง
  ไม่ควรอยู่ในกราฟตั้งแต่แรก ปลายทางของทุกเส้นทางคือ **หน้าอาคาร** ไม่ใช่ในตัวอาคาร
